# Схемы, события и контракты исполнения

Документ для разработки. Краткая эксплуатационная справка остаётся в содержимом модуля на русском и английском.

## Сцена и независимые схемы

Определения сохраняются в `Scene.flags.dmicher-master-screen.definitions.<schemeId>`, запуски — в `runtimes.<schemeId>`. ID схемы не зависит от её названия. `getDefinitions(scene)` возвращает упорядоченный список; `getDefinition(scene, {schemeId})` и `getRuntime(scene, {schemeId})` адресуют конкретную схему. У старого определения без коллекции схем сохраняется ID `main`. Сохранение конструктора не изменяет снимок выполняемого эпизода.

Схема содержит `schemeName`, `background`, `textColor`, `order`, `revision`, `episodes`. Цвета сохраняются в `#RRGGBB`. У эпизода есть `id`, `name`, `background`, `textColor`, `events` и прежние настройки объектов. Названия схем уникальны в сцене, названия эпизодов — в своей схеме, без различия регистра. Порядок задаётся полным списком ID, без пропусков и повторений.

`SchemeEditor(scene)` предоставляет:

- `list()`, `get(schemeId)`;
- `createScheme({name, background, textColor})`, `updateScheme(id, patch)`, `deleteScheme(id)`, `reorderSchemes(ids)`;
- `createEpisode(schemeId, {name, ...settings})`, `updateEpisode(schemeId, episodeId, patch)`, `deleteEpisode(schemeId, episodeId)`, `reorderEpisodes(schemeId, ids)`;
- `transferEpisode(fromSchemeId, toSchemeId, episodeId, {copy, name?})`;
- `exportScheme(id)`, `importScheme(envelope, {name?})`, `exportEpisode(schemeId, episodeId)`, `importEpisode(schemeId, envelope, {name?})`.

Изменения выполняются под локальной очередью записи сцены и требуют ГМ. Копия получает новый ID; перенесённый эпизод сохраняет ID, если он свободен в назначении. Области допуска собственных триггеров переназначаются на новую схему и новый ID копии. Старые прямые ссылки на соседние эпизоды при переносе отдельного эпизода снимаются; именованные события сохраняются и проверяются на неоднозначность в назначении. Уже выполняемый снимок исходного эпизода не переписывается и не запускается в принимающей схеме автоматически.

Сохранение существующих форм передаёт `{expectedRevision}`: для `updateScheme` и `updateEpisode` это ревизия определения, для `saveEvent`, `saveTrigger`, `saveMacro` — ревизия каталога. Проверка выполняется внутри локальной очереди до изменения данных; конфликт оставляет черновик формы для явного обновления. Это защита от устаревших локальных форм, а не серверная транзакция между двумя клиентами Foundry.

Схему с работающей автоматизацией нельзя удалить до её остановки. В сцене должна оставаться хотя бы одна схема. Активация не позволяет двум схемам одновременно управлять автоматизацией одного токена: конфликт сообщается до записи нового запуска. Ручное отключение токена в его схеме сохраняется до явного включения.

`EpisodeRuntime.enter(scene, episodeId, {schemeId, force?})` — явная команда ГМ; ограничения прежнего графа `allowFromAll/from` её не блокируют. Автоматический вызов обязательно указывает `{schemeId, expectedRunId, eventName}`; `eventName` должен входить в `events` целевого эпизода. Одно имя события не может вести в два разных эпизода одной схемы. Старые прямые цели зоны, взаимодействия НПС и проверки патруля при нормализации получают отдельные именованные маршруты, а старые подписки перехода — явную запись события в целевом эпизоде.

`halt(scene, {schemeId})` останавливает выбранную схему, `haltAll(scene)` сразу ставит локальные барьеры всем схемам и сохраняет их остановку. `enter(..., {schemeId, force:true})` — явное возобновление с выбранного эпизода. Переподключение не повторяет разовые эффекты. Запоздавшие ответы проверяют ID своего запуска. Асинхронный макрос патруля ожидается вне очереди записи; остановка и тики других объектов остаются доступны. Исполнение произвольного стороннего JavaScript нельзя насильно прервать.

Рабочие окна имеют отдельный жизненный цикл по схеме. Сессии магазинов и диалогов также адресуются `schemeId`. Один физический магазин не выдаёт параллельную сессию в другой схеме; подтверждённые остатки сохраняются на сцене по ID НПС в `shopInventories`, чтобы последовательная смена схем не восстанавливала проданные товары. Валюты и внутреннее количество предметов без адаптера не интерпретируются.

## Каталог сцены и типы триггеров

`EventCatalog(scene).list()` синхронно возвращает `{schemaVersion, revision, events, triggers, macros}`. Пользовательские записи хранятся в `eventCatalog`; встроенные определения добавляются кодом и защищены от изменения/удаления в сервисе. Старые имена событий в эпизодах представлены как явные записи и материализуются при первом редактировании каталога.

Событие: `{id, name, builtin, subscribers: []}`. Имя уникально в сцене. ID остаётся постоянным при переименовании. Изменение имени обновляет ссылки подготовленных эпизодов; уже запущенные снимки не переписываются. Удаление используемого события отклоняется до удаления его связей.

Тип триггера: `{id, name, eventId, builtin, parameters: []}`. Имя также уникально в сцене. Каждый параметр имеет `name`, `type`, `required` и ограничения:

| Тип | Ограничения |
| --- | --- |
| `string` | `minLength`, `maxLength`; длина в символах Unicode |
| `integer` | `min`, `max`; строка с цифрами числом не считается |
| `number` | `min`, `max`, `decimals` от 0 до 12; только конечное число |
| `boolean` | строго `true` или `false` |

Поле `type` в передаваемом объекте занято именем типа триггера. Неизвестные поля, несоответствие типа, нарушение ограничений и JSON длиннее 8000 символов отклоняются до регистрации. Параметры обязательны по умолчанию; `required:false` позволяет опустить поле. Имена параметров используют латиницу, цифры и подчёркивание, не допускают служебные имена прототипа. Объекты, массивы и исполняемый текст не являются пользовательскими типами параметров.

Пример объявления и вызова:

```js
const catalog = new EventCatalog(canvas.scene);
const event = await catalog.saveEvent({name: "guard.alert", subscribers: []});
const type = await catalog.saveTrigger({
  name: "guard.alert.signal", eventId: event.id,
  parameters: [
    {name: "level", type: "integer", min: 1, max: 3},
    {name: "heard", type: "boolean"}
  ]
});

await InvokeDmicherMasterScreenEvent("guard.alert", {
  type: "guard.alert.signal", level: 2, heard: true
});
```

Методы редактирования: `saveEvent`, `deleteEvent`, `saveTrigger`, `deleteTrigger`, `saveMacro({uuid, triggerIds})`, `removeMacro(uuid)`, `exportEvent(id)`, `importEvent(envelope)`, `exportTrigger(id)`, `importTrigger(envelope, {eventId?, name?})`. Импорт отдельного типа ищет родительское событие по имени либо использует явно выбранный `eventId`; отсутствие родителя и конфликт имени дают ошибку до записи. Встроенные события: `episode.entered`, `automation.changed`, `zone.entered`, `npc.interacted`, `patrol.arrived`, `patrol.check`, `dialogue.finished`. Их типы имеют такие же имена и набор заявленных параметров, доступный через `list()`.

## Подписанты, макросы и очередь

Подписанты события выполняются в порядке списка. Типы:

- `macro`: `macroUuid`; макрос должен быть зарегистрирован в каталоге сцены с принимаемым ID триггера;
- `trigger`: `triggerId`, `parameters`; из статических полей формируется валидируемый объект с `type` выбранного триггера и вызывается его событие;
- `builtin`: `action` из `pause`, `unpause`, `halt-scheme`, `halt-all`, `chat`. Для остановки схемы задаётся `schemeId`, для сообщения — `text` и явная `audience`.

Переход эпизода задаётся его таблицей событий. Дополнительного безусловного перехода среди новых встроенных подписантов нет.

Foundry исполняет скриптовый макрос вызовом `macro.execute({trigger, scene, event, screen, InvokeDmicherMasterScreenEvent})`; тем самым скрипт получает переменную `trigger`, а не строку, требующую `eval`. Дополнительные поля `scene`, `event`, `screen` сохранены для совместимости контекстных макросов. Локальная функция `InvokeDmicherMasterScreenEvent` привязана к сцене и запуску этого макроса: поздний ответ после остановки и нового запуска отклоняется. У `event` находятся ID запуска, исходная полезная нагрузка, аудит и контекст цепочки. Основной пользовательский договор — типизированный `trigger`.

Макрос проверки патруля получает такую же привязанную функцию вместе с прежними переменными `actor`, `token`, `scene`, `episode`, `runId`. При ручном обращении из стороннего JavaScript непосредственно к `globalThis` или API модуля исходный контекст автоматически определить нельзя; такое обращение не обладает договором локальной функции, переданной исполнителем.

`SceneEvents.invoke(scene, name, trigger)` и опубликованный `InvokeDmicherMasterScreenEvent(name, trigger)` требуют выбранного активного полного ГМ и запущенную схему. Возвращаемый Promise означает **приём в очередь**, а не завершение всех макросов. Поэтому макрос может `await` вызов следующего события без ожидания своей же очереди. В тестах или диагностике вне выполняемого подписанта завершение ожидается через `SceneEvents.whenIdle()`; из самого макроса ждать `whenIdle()` нельзя.

При приёме фиксируются действующие запуски схем. Подписанты каталога выполняются один раз; затем выполняются подходящие прежние подписки снимков эпизодов и разрешённый маршрут каждой схемы. Таким образом одно событие может независимо переключить две схемы. Остановленная схема или схема с уже изменившимся запуском пропускает устаревшее действие. Ошибка подписанта прекращает оставшуюся цепочку этого события и попадает в журнал. Уже выполненные действия не отменяются. Записи журнала и квитанции после переподключения не воспроизводятся.

Очередь событий упорядочена на клиенте ведущего ГМ. Пока запуск актуален, ожидаемый асинхронный подписант задерживает следующие события этой очереди, но не держит очередь записи сцены. При остановке, смене запуска или уходе со сцены ожидание старого макроса отвязывается от очереди; новая схема может обрабатывать события, даже если прежний Promise никогда не завершится. Начатый JavaScript продолжает существовать: его поздний отказ обработан, результат не меняет новую квитанцию, локальный вызов события остаётся привязан к прежнему запуску. Пределы — 32 уровня вложения и 64 события одной цепочки; превышение создаёт видимую ошибку в журнале. Локальная очередь не является сетевой авторизацией: команды игроков проверяются по автору Foundry, правам, текущей сессии и ID запуска.

## Перенос

JSON схемы/эпизода содержит подготовленное определение и зависимые события, типы триггеров и сведения о подключённых макросах. Импорт создаёт новое определение без текущего запуска, счётчиков, торговых сессий и игровых остатков. Совместимые одноимённые контракты принимающей сцены используются повторно; несовместимые ограничения или подписанты дают явную ошибку до сохранения. Ссылки на реальные токены, макросы и медиа сохраняются для проверки мастером; импорт отдельных настроек не создаёт автоматически эти документы.

Полный экспорт сцены дополнительно переносит все схемы и каталог, собирает документы поддерживаемых типов и переназначает UUID созданных документов. JSON старого формата с одним `definition` продолжает импортироваться. Произвольные строки пользовательских параметров не переписываются как предполагаемые ссылки.

Проверки: `tests/scene-design.test.js`, а также существующие наборы `runtime`, `events`, `model`, `shop`, `dialogues`, `transfer`, `workspace`. Проверены независимость двух запусков, общий fan-out события, неоднозначность маршрутов, границы типов, порядок подписантов, нативный контекст макроса, вложенный вызов без блокировки, предел циклической цепочки, конфликт владения токеном и перенос зависимых контрактов.
