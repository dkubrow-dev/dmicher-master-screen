# Каталоги инструментов и владение объектами

Этот документ описывает контракт подготовки сцены. Исполнение, торговые сессии и проверки сетевых команд описаны в [catalog-interactions-runtime.md](catalog-interactions-runtime.md). Примеры используют синтетические ID.

## Данные и ответственность

`Scene.flags['dmicher-master-screen'].interactionCatalog` хранит `{schemaVersion:1, revision, shops:[], dialogues:[]}` независимо от схем. Чтение каталога, списка объектов или схем не записывает флаги, не создаёт скрытую схему и не запускает эпизод. Мастер может подготовить самостоятельный инструмент до его назначения объекту.

Магазин: `{id,name,description,img,display,requireGMApproval,items}`. `display` — `list` или `tiles`; товары — `{id,data,stock}`. `data` содержит целый документ Item с `name` и `type`, остальные поля остаются непрозрачными для ядра. `stock` — строго целое число от 0 до 10000, без преобразования строк. Введённые здесь остатки — подготовка; расходованные товары и сессии не восстанавливаются при изменении описания, владельца или сохранении схемы. Один ID магазина у нескольких объектов означает общий склад и одну эксклюзивную торговую сессию.

Диалог: `{id,name,description,startPageId,pages}`. Страница — `{id,name,text,art,responses}`; ответ — `{id,label,nextPageId,eventName}`. Ответ либо продолжает диалог, либо завершает его с событием. Ссылка на отсутствующую страницу или событие отвергается. Текст не исполняется как код. Имена магазинов и имена диалогов уникальны каждый в своём каталоге без учёта регистра. Описания — строка либо `{ru,en}`.

`objectBindings` хранит `{schemaVersion:1,revision,bindings:{'Token:npc':binding}}`. Типы нативных объектов: Token, Tile, Drawing, AmbientLight, AmbientSound, Note, MeasuredTemplate, Wall, Region. Объект без настройки не требует пустой записи. Список объектов схемы выводится из этого единственного источника владения.

```js
const binding = {
  type: "Token", id: "npc", schemeId: "market", tags: ["merchant"], notes: "...",
  entry: { position: { x: 100, y: 200 }, hidden: null },
  episodes: { open: { position: null, hidden: false } },
  shop: { shopId: "stock", episodeIds: ["open"], range: 5, trigger: {} },
  dialogue: null,
  features: [{ id: "arrival", kind: "trigger", enabled: true, episodeIds: ["open"],
    eventName: "guard.observed", triggerId: "custom-result", parameters: { ok: true } }],
  playerCharacter: false, routines: []
};
```

Объект имеет одного владельца `schemeId` либо `null`; одну ссылку на магазин и одну на диалог. Магазины и диалоги назначаются только Token/Tile. Пустой `episodeIds` означает все эпизоды владельца. `trigger` использует действующий договор допуска: enabled, schemeIds, episodeIds, allowTags, denyTags, repeat, limit, resetOnEntry. Теги принадлежат явной привязке объекта сцены и читаются через `getObjectTags`.

`entry` хранит начальное положение и видимость, `episodes[id]` — правило явного входа в эпизод. `null` означает отсутствие команды изменения. Координаты конечные; объект должен поддерживать x/y. Сохранение этих полей не перемещает документы. У каждой схемы обязательный `entryEpisodeId`, существующий в её списке эпизодов; он выбирается только для явного запуска без указанного эпизода. В схеме с одним эпизодом он всегда входной; отсутствующее поле получает это единственное значение при чтении без записи. При нескольких эпизодах выбор обязателен. Перезагрузка и открытие сцены не являются запуском. Перед удалением или перемещением эпизода входа требуется выбрать другой.

## Узкие сервисы

Все команды требуют GM, работают под `withSceneLock` и проверяют `options.expectedRevision`, если он передан. Это защита устаревшего локального редактора, не распределённый CAS между браузерами. Черновик нужно сохранять с revision, полученным при его открытии.

- `new SceneAssets(scene).list()` возвращает каталог; `getShop(id)` и `getDialogue(id)` — запись или null. `saveShop(value, options)` и `saveDialogue(value, options)` принимают полную запись. `deleteShop`/`deleteDialogue` отвергают удаление инструмента, пока на него есть привязки.
- `new SceneObjects(scene).list()` возвращает envelope; `get({type,id})` — привязку или null; `save(descriptor, patch, options)` принимает только изменённые поля. `remove(descriptor, options)` снимает владельца. Теги и заметки сохраняются.
- `listNativeSceneObjects(scene)` возвращает нативные объекты с типом, ID, именем, UUID, текущими координатами и видимостью. `getSchemeObjects(scene, schemeId)` присоединяет текущую привязку; отсутствующий документ имеет `missing:true`. `getSceneObject(scene, descriptor)` возвращает документ либо null.
- `resolveObjectShop`/`resolveObjectDialogue(scene, descriptor, {schemeId,episodeId})` возвращают `{asset,binding,config}` либо null. Они не расходуют допуск и не проверяют право конкретного игрока: это делает исполнитель. Конфигурация диалога адаптирует `pages/startPageId` к `nodes/startNodeId`, магазин получает `shopId`, оба получают `target`.
- `materializeEpisode(scene, definition, episode)` создаёт отдельный снимок с `shops`, `dialogues`, `objects`, объектными подписками и распорядками. Исходная подготовка и текущий runtime не изменяются. Перед новым запуском исполнитель использует этот снимок.

Смена владельца требует `allowReassign:true` и остановки затронутых схем. При смене очищаются прежние entry, episodes, shop, dialogue, features и routines; поля, явно переданные в той же команде, проверяются в новой схеме. Заметки, теги и признак персонажа игрока остаются. При `schemeId:null` все правила и ссылки очищаются независимо от patch. Интерфейс должен заранее объяснять этот сброс. Обычное изменение заметок передаёт только заметки. Исполнительные `episode.tokens`, `dialogues` и `subscriptions` строятся из явных привязок как отдельный DTO, а не читаются из второй модели подготовки.

## Особенности и ссылки

Объектовая подписка в `features` содержит `id,kind,enabled,episodeIds,eventName,macroUuid,triggerId,parameters`. `kind` — `macro` или `trigger`.

Движение, ожидания, реплики и эмоции Token задаются шагами распорядка. Смена эпизода происходит через зарегистрированное событие и явное разрешение маршрута в целевом эпизоде.

Макросная особенность подписывается на существующее `eventName` и использует макрос из каталога Ширмы. Триггерная особенность подписывается на событие и вызывает другой типизированный триггер со статическими `parameters`. Параметры проверяются по типу при сохранении; изменение объявления триггера также проверяет существующие особенности. Исполнитель получает `target` и `featureId`, чтобы проверить актуальное владение и ручное отключение объекта.

Переименование события обновляет ссылки в независимых диалогах, особенностях, шагах распорядков и подготовленных эпизодах. Удаление события, триггера или макроса с используемой ссылкой отвергается. При удалении эпизода его объектные переходы удаляются; ограниченный только этим эпизодом магазин/диалог снимается, особенность отключается. Исчезнувший единственный scope не превращается в пустой список со значением «все эпизоды».

## Текущая модель и перенос

Читаются только явные коллекции `definitions`, `runtimes`, `interactionCatalog`, `eventCatalog` и `objectBindings`. Неподдерживаемые виды особенностей не включаются в текущий снимок и не мешают чтению актуальных распорядков. Старые формы подготовки не преобразуются в новые объекты и не исполняются через адаптеры. Миграций нет; их добавление требует отдельного запроса владельца. Чтение и рефакторинг не изменяют данные живых миров.

Исполнитель исключает управление объектом из чужой схемы. Удаление схемы сохраняет каталоговые инструменты и очищает её привязки, но не исполняет другое состояние и не восстанавливает ресурсы.

`SceneAssets.exportShop/exportDialogue` и `importShop/importDialogue` используют `{format:'dmicher-master-screen',kind,version:1,data}`; диалог включает зависимый каталог событий. `SchemeEditor.exportScheme/exportEpisode` включает необходимые ассеты и привязки вместе с типизированными событиями. Импорт переназначает локальные ID, scope схемы и эпизода, разрешает совпадающие контракты по имени, отвергает конфликтующее содержание или другого владельца объекта до записи. ID нативных объектов сохраняются; отсутствующий объект нужно назначить/восстановить отдельно. Макросные UUID в таком JSON требуют доступного документа; полный экспорт сцены переносит и документы зависимостей.

Импорт эпизода в ту же схему объединяет совпадающие области действия без дублирования подписок и распорядков и без изменения прежнего допуска. Копирование или перенос в другую схему не дублирует владение: при наличии настроек объектов исходной схемы команда отвергается с объяснением. Мастер предварительно разделяет или явно переназначает объекты. Каталоги остаются независимыми от удаления эпизода.

Полный JSON сцены содержит `interactionCatalog` и явные `objectBindings`; расходованные runtime, активные сессии и очередь исполнения не экспортируются. Пустая сцена экспортируется с нулём схем и импортируется так же. Проверка всего пакета и зависимых ссылок выполняется до создания документов.

Проверки: `tests/scene-assets.test.js` использует синтетические документы и воспроизводит рекурсивное слияние флагов Foundry с удалением map-ключей. `tests/scene-design.test.js` проверяет явное владение, остановку перед переназначением, перенос контрактов и отсутствие принятия старых форматов. Исполнитель и авторизация проверяются отдельно в `tests/catalog-interactions.test.js`.

## Персонажи игроков, распорядки и удалённые объекты

`binding.playerCharacter` — строго boolean, по умолчанию false; допустим только для Token. True исключает объект из источников автоматизации нового снимка: положения при входе, реплик, магазинов, диалогов, адресных подписок и распорядков. Подготовка сохраняется. Исполнитель дополнительно читает актуальный флаг перед действиями уже запущенного эпизода. Это разрешает роль взаимодействующего персонажа вне схемы, но не подменяет права владения Actor, дистанцию, видимость и теги. При снятии флага подготовка не запускается командой сохранения.

`binding.routines` — массив, по умолчанию пустой. Один блок `{episodeId,repeat:false,steps:[]}` на эпизод. Только Token. Шаг: `{id:1,kind,parameters,next:[2]}`. `next:[]` завершает цепочку; несколько ID означают выбор исполнителем одного следующего шага. Повтор регулирует возврат к шагу 1 после терминала. Нормализация находится в `routine-model.js` и не выполняет действий.

| kind | parameters | Проверка |
|---|---|---|
| wait | `{seconds:1}` | Конечное число больше нуля |
| move | `{x:0,y:0,speed:5}` | Конечные координаты; скорость больше нуля |
| speech | `{text:'',chat:true,bubble:true}` | Текст; хотя бы один способ вывода; строгие boolean |
| emotion | `{emoji:''}` | Одна видимая графема Unicode либо пустая строка для снятия эмоции |
| event | `{eventName:'',triggerId:'',parameters:{}}` | Существующее событие и принадлежащий ему триггер; строгая проверка типизированных параметров |
| macro | `{macroUuid:'',parameters:{}}` | Макрос из каталога Ширмы; параметры содержат только JSON |

Экспорты: `ROUTINE_STEP_KINDS`, `routineStepTemplate(kind)`, `normalizeRoutineStep(raw)`, `normalizeRoutine(raw)`, `normalizeRoutines(raw)`. Шаблон возвращает независимый черновик `{kind,parameters,next:[]}` без ID. Перед сохранением редактор выбирает ссылки события/макроса. Допускается до 200 шагов и 100 блоков. ID исходных шагов — уникальные положительные целые числа. Порядок массива задаёт только визуальный порядок строк: перетаскивание и сохранение сохраняют ID и `next`. Непустой блок обязательно содержит ID 1; исполнение и повтор начинаются с него. Новый шаг получает `max(id)+1`. Ссылки на удалённый шаг удаляются без перенумерации и произвольного перенаправления. Строки, выдаваемые за числа или boolean, отвергаются, как и неизвестные поля параметров.

`materializeEpisode` передаёт исполнителю `episode.routines:[{...routine,target:{type:'Token',id}}]`. Пустой блок ничего не выполняет. Распорядок — единственный источник пошагового поведения токена; удаление блока не включает другую модель исполнения.

Каталог событий проверяет ссылки рутин при удалении и редактировании типов; переименование события обновляет параметры шага. JSON эпизода/схемы переносит блоки и связанные event/trigger/macro-контракты, переназначает эпизодные и триггерные ID. Полный JSON сцены также включает документы макросов. Нельзя переместить такой эпизод в другую схему, незаметно продублировав владение объектом.

`SceneObjects.remove` для отсутствующего документа удаляет явную запись привязки. Каталоговые инструменты сохраняются независимо, текущие состояния запусков не переписываются. Проверки требуют GM и актуального expectedRevision, но отсутствующий документ не мешает очистке. Повторное чтение не воссоздаёт orphan, поскольку другой источник привязок отсутствует. Для существующего объекта действует прежний договор явного снятия владельца.
